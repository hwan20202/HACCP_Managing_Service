## SQL 검토 (0001)

현업 미팅 결과와 대조한 결과, **테이블 대부분은 그대로 유지**합니다. `main` merge 전이라 수정은 가능하지만, 이미 `init` 한 개발 DB는 지우고 다시 만들어야 합니다 (`data/db/app.sqlite3` 삭제 → `init` → `seed_master --sample`).

| # | 위치 | 내용 | 판단 |
|---|---|---|---|
| 1 | 머리말 C3 | `INCOMING_JUDGED` 의 CONDITIONAL, "CONDITIONAL → lot_holds" | 주석 수정 (PASS/FAIL 확정) |
| 2 | 머리말 C2 | subject_type 에 `BATCH` 없음 | 주석 수정 (10/11 확정 후) |
| 3 | 머리말 | "다음 마이그레이션: 생산지시" | 주석 수정 → 제조배치 |
| 4 | `lot_holds` CHECK | `(source_type = 'PROPAGATED') = (parent_hold_id IS NOT NULL)` 는 **LOT HOLD 에서만 전파**를 가정. 배치 HOLD 에서 LOT 로 전파하면 부모가 `lot_holds` 가 아니라서 이 CHECK 에 걸림 | ⛔ **10/11 에 HOLD 모델 정하고 수정** (SQLite 는 CHECK 변경 = 테이블 재생성이라 merge 전에 해야 함) |
| 5 | `lot_holds` 섹션 주석 | "이번 주는 CONDITIONAL 판정에만 사용" | 주석 수정 → CCP 이탈·수동 보류용 |
| 6 | `incoming_receipts.lot_id UNIQUE` | 입고 건별 LOT — 10/7 현업과 일치 | 유지. 멘토링의 "소비기한 기준 LOT" 안만 10/11 에 최종 배제 확인 |
| 7 | `domain_event_inbox` | 질의 5 가 직접 호출로 정해져 쓰이지 않음 | 10/11 ERD 정리 때 `lot_holds` 와 함께 삭제 (모델 1개 포함) |
| 8 | `v_stock_ledger` | `lot_id`, `item_id` 없음. D04 는 `stock_ledger()` 를 쓰므로 급하지 않음 | 0002 에서 뷰만 다시 만들어 컬럼 추가 (0001 수정 불필요) |
| 9 | `lot_number_rules` 토큰 | `{received:…}` 이름이 생산 LOT(제조일)에 어색 | ✅ 코드에 `{date:…}` 추가 (스키마 변경 없음) |
| 10 | `items` | 포장 규격(10g·100g·1kg)을 같은 품목으로 볼지 | 스키마 변경 없음. 규격별 코드면 품목 추가, 같은 코드면 g 단위 차감 |
| 11 | `stock_movements` 원천 연결 | 생산 투입·산출이 어느 배치인지 | 0001 변경 없음. 0002 의 투입·산출 테이블이 `stock_movement_id` 를 가리킴 (입고와 같은 방식) |
