# 생산·수불 UI 재정리 및 데이터 유지 배포

> 수불 화면은 후속 수정에서 멘토 요구대로 **입출고 내역 + LOT별 현재고를 함께 표시**하도록 복원했다. 아래 탭 분리 설명보다 [최신 통합 화면·시나리오 결과](qa-overview-scenarios-20261016.md)를 우선한다. 생산·입고 개선과 데이터 유지 배포는 계속 적용한다.

## 반영 내용

PM MVP의 정보 배치를 기준으로 현재 Django API에 연결했다. 비교 근거는 [frontend-vs-pm-mvp-2026-10-16.md](frontend-vs-pm-mvp-2026-10-16.md).

- 생산 진입점을 **생산지시 · 실적**으로 통합했다. 기존 생산일지 경로도 같은 화면으로 이동한다. 고정 데이터 생산일지 화면으로 들어가지 않는다.
- **생산 계획 등록 / 생산 목록 · 실적 입력** 탭을 제공한다. 계획 입력 옆에서 저장 전 BOM 소요량·가용량·부족량을 조회한다. 미리보기는 배치나 수불을 저장하지 않는다.
- 계획 등록과 생산 시작은 계속 구분한다. 계획 등록만으로 재고가 차감되지 않는다.
- 시작 후 BOM 행의 **투입량 확인**을 누르면 남은 기준량을 기본값으로 LOT를 제안한다. 기준 원료를 우선 사용하고 부족분은 등록 대체 원료로 제안한다. 품목별로 소비기한·입고일 순서를 적용한다. 특정 원료만 선택할 수도 있다.
- LOT 수동 배분은 접힌 상세 영역에서 수정한다. 입력 총량과 선택 LOT 합계를 BOM 원료 단위로 환산해 비교하고, 다르면 화면과 서버에서 저장을 거부한다. 기존 일괄 롤백·중복 요청 방지·BOM 외 원료 차단은 유지한다.
- 생산의 연결 문서·재고 수불 이력은 별도 탭에서 확인한다.
- 수불대장은 **수불 내역 / 현재고** 탭으로 복원했다. 검색어는 이름·코드·LOT·공급처에 적용된다. 현재고는 품목별 한 줄이며 검색해도 재고 없는 품목을 이름·코드로 찾을 수 있다.
- 현재고에서 품목명을 누르면 LOT 목록이 열리고, LOT별 또는 품목 전체 수불로 이동한다. 총재고·사용 가능·사용 불가·최소재고·부족 표시를 유지한다.
- 수불의 입고/출고 필터, 빠른 기간 선택, 현재고의 부족 품목·소비기한 조회·kg/g 표시 전환을 제공한다. 기간은 기존 API 제한에 맞춰 최대 1년이다. 2년 조회는 이번 반영에 포함하지 않았다.
- 엑셀은 표시 중인 검색·입출고 필터와 같은 결과를 내려받는다. 품목코드·LOT는 문자열, 수량은 숫자 셀로 저장하며 수량 단위는 기준 단위다. PM MVP의 외부 의존성 없는 XLSX 작성기를 재사용했다.
- QA 입고는 현재 메뉴의 품목 유형을 기본값으로 한다. 원료·포장재·반제품·전체 유형을 선택할 수 있고, 검색 결과를 4행 목록에서 바로 선택한다. 유형을 표시하고 kg/g 입력을 기준 단위로 정확히 환산한다.

## 검증 기록

- 프로젝트 필수 검사 `scripts/project.py check`: 의존성·ruff·포맷·배포 스크립트 테스트·Django 설정/마이그레이션 검사 통과. Django 781건 실행, 33건은 각 테스트의 조건에 따라 건너뜀. 건너뛴 검사를 통과한 것으로 세지 않는다.
- 새 API 검증: 저장 없는 계획 미리보기와 생성 후 준비 상태의 일치, 대체 원료 kg/g 혼합 자동 배분, 총량 불일치 시 저장 거부 및 재고 불변, 정상 일괄 저장·재전송·변경 요청 키 거부, 코드·이름·공급처 검색과 CSV 일치.
- `node scripts/test_qa_frontend.cjs`: 후보 제한, 소수 정밀도, kg/g 합계, 검색 조건·입출고 필터 확인.
- 파일 SQLite의 일괄 투입 동시성 2건 별도 통과: 동일 요청 재전송과 같은 재고 경쟁 투입. 위 전체 검사에서 건너뛴 항목 중 해당 2건을 추가 실행한 것이다.
- 실제 Chrome 브라우저: 격리된 **새 로컬 QA 데이터**에서 계획 미리보기 → 계획 등록 → 시작 → 자동 배분 → 수동 합계 불일치 차단 → 투입 → 산출 → 완료, CCP 3종 연결, 수불 추적 통과.
- 같은 브라우저에서 수불 검색·출고 필터·엑셀 전달 데이터 일치, 현재고·품목 LOT 모달, 입고 품목 유형·검색·500g 입력의 0.5kg 저장, 820px 너비에서 페이지 가로 넘침 없음 확인. JavaScript 예외 0건.
- 브라우저 검증 스크립트: `scripts/test_qa_browser.cjs`. 루프백 8018/Chrome CDP 9337을 사용하며 **prepare 단계의 별도 새 QA DB에서만** 실행한다. 현재 호스팅 QA를 대상으로 실행하지 않는다.
- 로컬 캡처·브라우저 보고서: Git 제외 `tools/qa-ui-results/`. 기존 로컬 업무 DB나 호스팅 QA에 검증 거래를 기록하지 않았다.
- 실제 iPad/Safari와 호스팅 서버의 수정 후 업무 검증은 별도다.

## 재배포 및 데이터 보존

**이번 배포는 기존 QA 데이터를 유지한다. 기존 시나리오 문서의 ‘새 QA 데이터로 한 번 교체’ 절차는 이번 배포에 사용하지 않는다.**

1. 검증한 변경을 커밋한 후 `.venv/Scripts/python.exe scripts/package_cafe24_qa.py`로 패키지를 만든다. 기본 실행문에는 `--fresh-data-once`가 없다.
2. 생성한 `tools/qa-deploy/redeploy-<커밋>/upload-and-deploy.ps1`을 사용자 터미널에서 실행하면 scp로 업로드하고 ssh로 배포한다. SSH 비밀번호가 필요하면 터미널에서 입력하며 파일이나 채팅에 저장하지 않는다.
3. 기존 재배포 스크립트는 쓰기를 중지하고 기존 DB·WAL·첨부·코드·환경을 백업한다. 같은 데이터 경로를 유지하고 migrate·collectstatic·설정/수불 무결성을 검사한 뒤 코드를 전환한다. 일반 코드 배포에는 Seeder와 양식 재설치를 실행하지 않는다.
4. 쓰기 중지 상태에서 배포 전후 업무 테이블 전체 행의 해시를 비교한다. 재고 수량 변경도 감지하며, 다르면 배포를 중단한다. Django 마이그레이션 적용 이력과 SQLite 내부 테이블은 비교에서 제외한다. 이번 변경에 새 마이그레이션은 없다.
5. 원격 배포 결과·기존 버전·데이터 유지 확인은 서버의 `deployment.json`에 기록한다. 실패하면 기존 코드·환경을 복원하고 데이터를 삭제하지 않는다.
6. 배포 완료 후 브라우저를 새로고침하고, 기존 입고·배치·문서가 보존됐는지 확인한다. 먼저 새 계획의 미리보기와 기존 배치 조회를 확인한 뒤 업무 QA를 재개한다.

이번 세션에서 SSH 연결은 가능했지만 `publickey,password` 인증이 거부됐다. 서버 파일 변경이나 서비스 재시작은 실행하지 않았다. 로컬 검증 성공과 원격 배포 완료를 구분한다.
