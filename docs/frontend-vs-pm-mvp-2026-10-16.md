# PM MVP와 현재 생산·수불 화면 비교

작성일: 2026-10-16

## 검토 범위와 결론

- 기준 원본: `D:/project/biodot/HACCP-0.1.1-windows-x64(정환MVP)/app/`
- 현재: `frontend/static/prototype/js/modules/inventory-api.js`, `production-api.js`, 메뉴 연결 `app.js`, 관련 서버 서비스.
- 코드 검토 결과다. MVP 실행, 현재 브라우저 화면 비교, QA 서버 재검증은 하지 않았다. 화면·서버·DB·QA 데이터는 변경하지 않았다.
- 전달받은 답변이 언급한 동일 이름의 비교 문서는 현재 저장소에서 발견하지 못해 이 문서를 새로 작성했다.

**현재 문제는 편의 기능 몇 개의 과잉 추가뿐 아니라, PM 화면을 API 중심의 별도 화면으로 바꾼 데 있다. PM의 정보 배치와 조작 흐름을 기준으로 복원하면서 현재 업무 규칙과 서버 검증을 연결하는 것이 적절하다.**

`docs/inventory-frontend.md`에도 메뉴·표·탭·모달은 시제품과 같게 유지하고 데이터 처리를 API로 교체한다고 명시되어 있다. 현재 수불 화면은 이 방향과 다르다. 다만 이 문서가 설명하는 고정 데이터 시제품과 사용자가 지정한 실행 패키지의 MVP는 같은 구현 상태가 아니다. 지정한 MVP에는 이미 서버 검색·재고 집계·작업지시 등록 API가 있다.

## 사용 흐름 비교

| 작업 | 지정한 PM MVP | 현재 API 화면 | 판단 |
|---|---|---|---|
| 수불 검색 | 수불 탭에서 코드·이름·공급업체/거래처·LOT 검색을 서버 조회에 적용 | 검색어가 품목 드롭다운 후보만 좁힘. 실제 조회는 별도 품목 선택·LOT 조건 | 원래 검색의 목적을 복원해야 한다 |
| 현재고 검색 | 현재고 탭에서 이름·코드·LOT 검색 | 수불과 공유하는 품목 선택·LOT 조건 | 탭별 검색 대상과 조건을 명확히 해야 한다 |
| 정보 배치 | 수불 내역 / 현재고 탭 | 품목 합계 → LOT 재고 → 수불 이력, 세 표를 세로 배치 | 기본 화면을 탭으로 복원하고 LOT는 상세에서 확인 |
| 빠른 조회 | 입고/출고 구분, 기간 버튼, 소비기한 기준 전환 | 날짜 입력과 소비기한 상태·사용 가능·0재고 등 조건을 함께 노출 | 자주 쓰는 조건을 앞에, 예외 조회는 상세 조건으로 이동 |
| 현재고 단위 | 품목별 합계, 부족·주의 요약 및 필터, 품목 이력 진입 | 품목 합계 표와 LOT 표 분리 | 품목 합계 중심으로 정리하고 총재고·가용재고 정보를 결합 |
| 입고 품목 선택 | 현재 원료/부자재 화면의 품목, 검색 아래 4행 목록상자 | QA 모달에서 원료·포장재·반제품을 모두 조회해 단일 드롭다운 제공 | 현재 메뉴 유형을 기본값으로 하고 전체 유형 선택은 명시적으로 제공. 유형 표시 추가 |
| 입고 수량·LOT | 단위 선택·환산 UI, LOT 입력·자동 생성 보조 | 기준 단위 수량 입력, 서버 채번 | 환산 편의는 복원하되 저장 단위·채번 규칙은 서버 기준 유지 |
| 생산 준비 | 입력 폼 오른쪽에 BOM 필요량·가용량·충분/부족 미리보기 | 배치 생성 후 상세에서 준비 상태 표 확인 | 저장 전 미리보기를 복원할 가치가 높음 |
| 생산 처리 | 작업지시 등록 시 BOM 원료·부자재를 FEFO로 자동 불출 | 계획 → 시작 → 원료별 품목/LOT·수량 선택 → 투입 → 산출 → 완료 | 계획/시작 분리는 유지하고 LOT 조작을 간소화 |
| LOT 분할 | 서버가 여러 LOT 자동 배정 | 총량 입력 → 배분 요청 → 체크·수량 확인 → 저장 → 추가 확인창 | 자동 제안 요약을 기본으로, 수동 분할표는 필요할 때 펼치기 |
| 내보내기 | `.xlsx` 생성 | 수불 CSV | 엑셀 업무 편의 복원 대상 |

## 유지할 변경

- **BOM 및 등록 대체 원료 검증:** `production.resolve_bom_line()`이 허용되지 않은 품목·잘못된 BOM 행을 차단한다. 프론트 후보 제한과 서버 차단을 함께 유지한다.
- **생산 시작 전 가용재고 검사:** `start_batch()`에서 준비 상태를 검사한다. 등록 후 시작을 분리한 현재 흐름에 필요한 검사다. 재고 예약과는 다르므로 실제 투입 시 재검사도 유지한다.
- **대체 원료 공유 재고의 중복 계산 방지:** `material_readiness()`가 여러 BOM 행이 공유하는 대체 원료를 함께 계산한다.
- **일괄 투입 원자성과 중복 요청 방지:** `add_usages()`의 전체 롤백 및 요청 키 재처리를 유지한다. 긴 화면과 별개인 서버 안전장치다.
- **총재고·가용·사용 불가 구분:** 검사대기·부적합·보류 등을 구분하는 정보는 필요하다. 다만 이를 위해 별도 합계 표를 항상 추가할 필요는 없다.
- **소비기한 있음·없음·미확인 구분과 서버 LOT 채번:** 입고와 기존 데이터의 의미를 보존한다.
- **계획/시작, 실제 투입/산출의 구분, CCP 문서 연결, 취소 배치 기본 제외, LOT 잔량 명칭:** 업무 흐름과 추적에 도움이 되는 변경이다.

## 우선 수정할 지점

1. **수불 검색을 결과 조회와 연결한다.** 검색어가 드롭다운만 바꾸는 현재 동작을 없애고 코드·이름·LOT·공급업체 등 해당 탭의 검색 대상으로 연결한다. 검색 조건과 내보내기 조건을 일치시킨다. 화면에 보이는 일부 행만 필터하는 방식으로 구현하지 않는다.
2. **수불/현재고 탭과 품목 상세를 복원한다.** 기본 현재고는 품목당 한 줄, 품목 클릭 후 LOT 및 수불 이력 확인. LOT 정보 자체는 없애지 않는다.
3. **QA 입고 선택을 명확하게 한다.** 유형 표시, 현재 메뉴 유형 기본 선택, 검색 결과를 바로 선택할 수 있는 목록을 제공한다. 반제품 입고는 서버가 허용하므로 메뉴 기본값을 준다는 이유로 기능을 차단하지 않는다.
4. **생산에서 BOM 행 선택을 중심으로 한다.** 선택한 BOM 행의 기준 원료·등록 대체 원료만 보여 준다. 현재 검색 드롭다운은 배치 전체의 BOM 행 후보를 합친 구조라, 후보 수가 항상 1~3개라고 단정할 수 없다. 전체 후보 검색을 기본 조작으로 둘 필요는 없다.
5. **자동 배분 결과를 먼저 제시한다.** 입력 총량과 추천 LOT·배분량을 간단히 보여 주고, 변경이 필요할 때 수동 배분표를 펼친다. 자동 불출 도입 여부와 재고 차감 시점은 별개로 다룬다.
6. **총량과 실제 합계를 분명히 한다.** 현재 `addUsage()`는 선택 LOT의 양수·소수 자리·합계를 검사하지만, 이 합계가 입력한 총량과 같은지는 검사하지 않는다. 서버 일괄 요청에도 목표 총량은 전달하지 않는다. 추천 총량과 다르게 투입할 때는 차이를 명시하거나 수정을 요구해야 한다. 이는 전부 성공/취소 보장과 별개의 문제다.
7. **표시·보조 기능을 복원한다.** 빠른 기간 선택, 입출고 필터, 엑셀, 단위 표시 환산을 지원하되 API 조건도 함께 검토한다.

## 전달받은 비교에서 보정할 부분

- **MVP는 단순 고정 데이터 화면이 아니다.** 지정 패키지의 `inventory.js`는 서버 검색을 사용하고 `production-wizard.js`는 작업지시 API를 호출한다. 원래 UI를 복원한다고 기존 API 코드를 그대로 복사할 수는 없다. 현재 Django API와 응답·업무 모델이 다르다.
- **MVP의 모든 화면 기능이 저장까지 완성된 것은 아니다.** 입출고 모달에는 LOT 선택 API 준비 전 출고/사용 등록이 저장되지 않는다는 안내가 있다. 보이는 버튼과 동작 완료 기능을 구분해야 한다.
- **자동 불출은 실제 MVP 서버 구현이 있다.** `backend/services/work-orders.cjs`는 등록 트랜잭션에서 재고 검사와 FEFO 불출을 수행한다. 현재 UI에 같은 기본 경험을 제공하는 것은 가능하지만, 현재 계획/시작 분리와 차감 시점을 정해서 연결해야 한다.
- **현재 배분 제안은 선택한 한 품목 안에서만 한다.** `proposeAllocation()`은 `item_id`와 총량으로 요청한다. 준비 상태가 대체 원료를 포함해 충분하더라도 기준 원료 한 품목의 FEFO 제안만으로는 총량을 채우지 못할 수 있다. BOM 행별 대체 후보 선택과 배분을 함께 설계해야 한다.
- **“총재고/가용 구분이 MVP에 전혀 없다”는 단정은 부정확하다.** MVP 생산 미리보기는 가용량을 사용하고 서버 재고 서비스도 가용·만료 수량을 계산한다. 현재의 품질 상태·보류를 포함한 구분을 유지할 이유와, 기존 기능 유무는 구분해야 한다.
- **“서버 수정은 대부분 좋다”는 표현은 전체 검증 결과가 아니다.** 위 검증·원자성 등의 구현은 확인했지만, 이번 검토에서 전체 테스트나 동시성·실제 QA 검증을 재실행하지 않았다.
- **2년 기간 버튼은 단순 UI 복사로 복원할 수 없다.** 현재 API의 최대 1년 규칙과 맞춰 서버 조회·기간 분할·내보내기를 설계해야 한다.
- **현재 생산 메뉴도 두 구현이 공존한다.** `app.js`에서 `production-log`는 기존 `ProductionPage`, `production-batches`는 `ProductionApiPage`로 연결된다. 실제 생산 업무의 진입점을 명확히 정리할 필요가 있다.

## 적용 순서와 확인 기준

먼저 수불/현재고 탭·직접 검색·입고 선택을 복원하고, 다음으로 생산 입력과 BOM 미리보기·LOT 배분을 정리한다. 이후 엑셀·표시 단위·기간 보조 기능을 연결한다. API와 데이터 모델은 현재 것을 기준으로 작업한다.

후속 구현에서 확인할 항목:

- 검색어 입력 후 표가 직접 바뀌고, 검색 해제 시 복원되며 내보내기도 같은 조건을 사용한다.
- 원료·포장재·반제품 입고를 구분해서 선택할 수 있고, 수량은 기준 단위로 저장된다.
- BOM 밖 원료는 화면·서버 모두 차단되고 등록 대체 원료는 선택 가능하다.
- 여러 LOT 자동 제안, 수동 수정, 총량 차이, 중복 클릭, 중간 LOT 실패 시 전체 롤백을 확인한다.
- 가용량 충분 판정과 대체 원료를 포함한 실제 투입 가능성이 일치한다.
- 계획 등록만으로 재고가 차감되지 않고, 정한 투입 시점에만 수불이 발생한다.
- 기존 QA 입고·LOT·배치·문서 데이터를 유지하고 변경 전후 잔량과 연결 관계를 비교한다.
