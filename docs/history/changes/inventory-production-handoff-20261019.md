# 입고 생산 재고 구현 현황과 QA 배포 인계

기준일: 2026-10-19 · 작업 브랜치: `feature/inventory-production` · 병합 대상: `main`

입고 → 제조 생산 → 벌크 반제품 산출 → 재고·수불 조회 흐름을 연결했다. 개발 중에는 이 작업 브랜치의 커밋을 로컬에서 패키징해 QA 서버로 전송·배포해 왔다. 이제 기능 변경을 `main`에 통합하고, 같은 배포 절차를 반복할 수 있도록 자동화하는 것이 다음 목표다.

사용자는 최신 기능을 배포했다고 확인했다. 이 문서 작성 중에는 서버 접속·배포·DB 적재를 실행하지 않았으며, 현재 서버의 정확한 커밋과 월별 추가 데이터 적재 상태를 독립적으로 확인하지 않았다. 과거 QA 문서의 ‘미배포’ 표기는 해당 문서 작성 당시의 작업 기록이다.

## 구현한 기능

| 영역 | 현재 구현 | 범위와 구분 |
|---|---|---|
| 입고 | 원료·포장재·구매 반제품 검색·선택, 소비기한 유무, 검사 판정, kg/g 환산, LOT·입고 수불·관련 문서 연결 | 입고 건별 내부 LOT 분리 유지 |
| 생산 계획과 시작 | BOM 소요·가용·부족량 미리보기, 계획 등록과 시작 분리, 재고 부족 시 시작 차단 | 계획 등록만으로 재고 차감 없음 |
| 원료 투입 | 사용 가능 LOT 자동 배분, 수동 분할, 등록 대체 원료, BOM 외 원료 차단 | 실제 투입 저장 시 차감 |
| 여러 원료 일괄 투입 | 기등록량을 뺀 남은 원료 제안, 한 표에서 수량·LOT 수정, 선택 원료 일괄 등록 | 원료별 합계 검증, 실패 시 전체 롤백, 재요청 중복 방지, 검토 후 변경 감지 |
| 산출과 완료 | 같은 배치의 산출 LOT에 분할 수량 누적, 완료 상태 처리 | 제조 산출물은 벌크 반제품 |
| 재고와 수불 | 원료·부자재·완제품 수불대장에 수불 내역/현재고 두 탭, 품목별 총재고·사용 가능·사용 불가 | 별도 재고·수불 현황 메뉴와 LOT 패널 제거 |
| 공통 품목 상세 | 현재 재고 요약 → 소진 LOT를 포함한 전체 LOT → 기간 수불, LOT 선택·전체 복원, 기간 변경 | 현재 잔량·종료일 잔량·거래 직후 잔량 구분 |
| 다운로드와 연결 | 탭별 범위·파일명이 반영된 XLSX, 품목 상세 4개 시트, 입고·배치·문서 진입 | 정정·반품·폐기 이력 조회와 신규 입력 화면 제공은 별개 |
| QA 데이터와 안내 | 최초 기준 데이터, 월별 가상 이력 추가 명령, 2쪽 사용 안내 | 월별 데이터는 코드 배포만으로 생기지 않음 |

입고·생산의 문서 생성/연결은 구현했다. 문서 작성·측정값 입력·결재·첨부 전체 흐름까지 이번 생산 QA에서 모두 검증했다는 뜻은 아니다. HOLD 서비스·API도 제공하지만, 모든 품질 업무의 화면과 정책이 확정됐다는 의미는 아니다.

## 현재 배포 방식

```text
feature/inventory-production의 검토된 커밋
  → 로컬 패키징과 SHA256 생성
  → SCP로 QA 서버 전송
  → SSH로 서버 재배포 스크립트 실행
  → 격리 회귀검사와 기존 데이터 백업
  → 설정·마이그레이션·정적 파일 검사와 코드 전환
  → 서비스 재시작 및 상태 확인
```

| 구성 | 현재 역할 |
|---|---|
| `.github/workflows/ci.yml` | push/PR에서 Windows·macOS·Ubuntu의 프로젝트 검사, 정적 파일 수집, HTTP 점검. 서버 배포 단계는 없음 |
| `scripts/package_cafe24_qa.py` | 깨끗하고 커밋된 작업 브랜치만 패키징. 커밋·파일 해시 manifest, 전송/실행 보조 스크립트 생성 |
| `scripts/redeploy_cafe24_qa.py` | 서버에서 해시·커밋 확인, 배포 잠금, 격리 검사, DB·첨부 포함 데이터와 설정 백업, 코드 전환·복원, 상태 확인 |
| 서버의 기존 영구 데이터 경로 | 일반 재배포 때 QA DB·문서·첨부·테스트 이력을 유지 |

일반 배포는 기존 데이터 경로를 유지하며 업무 테이블의 배포 전후 fingerprint를 비교한다. `--fresh-data-once`는 별도 데이터 공간으로 전환하는 예외 기능으로, 정기 배포와 자동 배포에 포함하지 않는다. 복원은 이전 코드·설정을 되돌리고 신규 데이터와 신규 코드는 남겨 두는 방식이며, 모든 DB 마이그레이션을 자동으로 역적용하는 절차는 아니다.

현재 패키징은 브랜치명과 비교 기준 커밋이 고정돼 있고, 전송 대상·계정·서버 경로도 특정 QA 설치에 맞춰져 있다. 재배포는 기존 관리자 실행 환경을 전제로 하며, 의존성이 바뀌면 별도 가상환경 준비를 요구한다. 이를 그대로 CI에서 실행하는 수준으로 자동화 완료라고 보기는 어렵다.

## 배포 자동화 후속 작업

이 PR은 기존 배포 절차와 자동화 방향을 정리한다. 아래 CD 파이프라인을 이번 PR에서 새로 구현하거나 활성화하지는 않는다.

1. **배포 기준을 커밋 SHA로 통일한다.** 패키징의 고정 작업 브랜치·비교 기준을 인자로 바꾸고, CI에서 검사한 커밋과 서버에 올리는 커밋이 같도록 기록한다.
2. **수동 실행형 QA 배포부터 만든다.** GitHub Actions에서 대상 커밋을 명시해 실행하고, 검사가 통과한 패키지를 배포 산출물로 보관한다. 서버 반영 단계는 검증·패키징 단계와 구분한다.
3. **서버 접속 설정을 분리한다.** 배포 계정·SSH 키·검증된 호스트 키·경로를 배포 환경의 설정으로 관리한다. 환경 파일·비밀번호·DB·첨부는 저장소나 공개 산출물에 포함하지 않는다. 기존 관리자 권한 전체를 그대로 넘기지 않도록 실행 권한을 정리한다.
4. **한 번에 한 배포만 허용한다.** CI 배포 동시 실행을 제한하고 서버의 기존 배포 잠금도 유지한다. 코드 전환 도중 새 실행이 끼어들지 않도록 한다.
5. **성공 조건과 복구 절차를 남긴다.** 커밋·해시·백업 경로·서비스 및 HTTPS 상태를 배포 결과에 기록한다. 실패 시 이전 코드 복원과 데이터 보존을 확인한다. 의존성·DB 스키마 변경은 별도 검토한다.
6. **QA 데이터 추가는 별도 실행으로 둔다.** 일반 배포에서 Seeder를 실행하지 않는다. 월별 이력이 필요할 때만 추가 명령의 적재 계획과 백업을 확인해 실행한다.
7. **안정화 후 트리거를 결정한다.** QA 수동 배포·복원 검증을 마친 뒤 `main` 병합 또는 릴리스 태그를 배포 시작점으로 정한다. 운영 배포는 환경과 절차를 분리한다.

자동화 완료 기준은 로컬 PC에서 파일을 보내지 않아도 지정 커밋을 QA에 재현 가능하게 반영하고, 기존 테스트 기록·문서·첨부를 보존하며, 실패·복원 결과와 배포 커밋을 확인할 수 있는 상태다.

## 기능과 운영의 남은 작업

| 구분 | 다음 작업 |
|---|---|
| 병합과 배포 이력 | `main` 통합 후 실제 QA 배포 커밋을 배포 기록과 대조. 과거 QA 문서는 작성 시점 기록으로 유지 |
| 현업 사용 확인 | 이사님께 간단 사용 안내 전달 후 용어·조회 범위·LOT 구분·일괄 투입 흐름에 대한 의견 반영 |
| 데이터 | 월별 QA 데이터 반영 여부 확인. 필요 시 기존 데이터에 추가하고, 실제 기준정보는 별도 범위로 검토 |
| 문서 연동 | 입고·배치 연결뿐 아니라 문서 작성·측정·결재·첨부의 전체 흐름을 담당 영역과 함께 검증 |
| 품질 정책 | 보류/해제와 문서 처리의 호출 주체·업무 기준 정리, 사용 가능 표시 정책 확인 |
| 운영 준비 | 로그인·권한, 백업 보관과 복구 실습, 접근 범위, 배포 계정과 장애 대응 절차 정리 |
| 범위 별도 협의 | 정정·취소·반품·폐기 입력 UX, 판매 포장·소분·포장배치, 출하·판매·고객 반품 |

마지막 행은 이번 MVP 완료 조건에 자동으로 추가하는 목록이 아니다. 필요성과 담당 범위를 협의한 뒤 진행한다.

## 검증과 참고 문서

- 입고·생산·재고의 서버 검증, 프런트 로직과 격리 브라우저 검증은 각 변경 문서에 기록했다. 일괄 투입에서는 기존 3건 보존/나머지 15건 제안, 선택 저장, 응답 유실 재시도, 실패 시 롤백을 확인했다.
- 이 PR 작성 시 `scripts/project.py check`를 실행했다. 의존성·Ruff·포맷·스크립트 테스트 5개·설정·마이그레이션 누락 검사를 통과했고, Django 테스트 797개는 실패 없이 종료했다(763개 통과, 별도 환경을 요구하는 34개 건너뜀). `node scripts/test_qa_frontend.cjs`도 통과했다. 서버 배포 상태와 로컬 검사 결과는 구분한다.
